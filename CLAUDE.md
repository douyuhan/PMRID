# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Code and pre-trained models for the ECCV20 paper "Practical Deep Raw Image Denoising on Mobile Devices" (PMRID). Originally a pure inference/benchmark repo (`Denoiser` + evaluation against a RAW image dataset); a training loop was added later (see Training below). **Every MegEngine script here has a PyTorch counterpart (`_meg` suffix vs. `_pytorch` suffix/no suffix) — prefer the PyTorch one** (`run_benchmark_pytorch.py`, `train_pytorch.py`) unless specifically reproducing MegEngine numbers: MegEngine has no installable wheel on this project's Windows dev machine, so its scripts can't actually be run here at all, only read/edited.

There are two parallel benchmark scripts, kept in sync by hand:

- `run_benchmark_meg.py` — the original script, runs the **MegEngine** model (`models/net_mge.py` + `models/mge_pretrained.ckp`), loading weights via `pickle` rather than MegEngine's own checkpoint API. Only supports `BGGR` bayer input and doesn't save any images.
- `run_benchmark_pytorch.py` — runs the **PyTorch** model (`models/net_torch.py` + `models/torch_pretrained.ckp`) instead, loading weights via `torch.load`/`load_state_dict`. Adds two things the MegEngine script doesn't have: support for all four bayer patterns, and a `--save-dir` option to dump visualizations (see below). On this project's Windows dev machine, MegEngine has no installable wheel, so **prefer `run_benchmark_pytorch.py`** unless you specifically need to reproduce the MegEngine numbers.

**Run all python commands in this repo inside the `AIISP_init` conda env** (`conda run -n AIISP_init python ...`) — it has `torch`/`numpy`/`opencv-python`/`scikit-image` installed; MegEngine is not installed there (and has no Windows wheel).

```
conda run -n AIISP_init python run_benchmark_pytorch.py --benchmark /path/to/PMRID/benchmark.json models/torch_pretrained.ckp --save-dir /path/to/output
```

- Requires `Python >= 3.6`.
- There are no tests, lint config, or CI in this repo.
- The scikit-image version in `AIISP_init` (0.26) no longer accepts `structural_similarity(..., multichannel=True)` — use `channel_axis=-1` instead (already done in `run_benchmark_pytorch.py`).

## Dataset layout

`dataset/benchmark/` (gitignored data, not the code) mirrors the structure described in the README: `benchmark.json` holds metadata for every sample, and each entry points at `input.raw`/`gt.raw` — raw uint16 Bayer buffers — under `SceneN/{Bright,Dark}/exposure-caseN/`. `dataset/benchmark.py::BenchmarkLoader` parses `benchmark.json` into `RawMeta` dataclasses and iterates over `(input_bayer, gt_bayer, meta)` triples, resolving relative file paths against the JSON's parent directory (or an explicit `base_path`).

Per-sample metadata (`RawMeta`) carries everything needed to turn a raw Bayer image into a comparable RGB image: `bayer_pattern` (one of `RGGB`/`BGGR`/`GRBG`/`GBRG` — the original Reno 10x dataset is always `BGGR`, but the loader/utils accept any of the four), `ISO`/`exp_time`, `wb_gain`, `CCM` (3x3 color correction matrix), `ROIs` (patch regions used for PSNR/SSIM), and `raw_bitWidth` (bit depth of the raw `.raw` files, default `16` when a dataset's json omits it — used by `BenchmarkLoader._load_idx` to normalize to `[0,1]` via `2**raw_bitWidth` instead of assuming 16-bit; the Reno 10x benchmark data is 16-bit, but `dataset/test/meta_info.json` is a user-supplied 12-bit dataset).

**Normalization convention (as specified by the user, not invented)**: every int↔float conversion of a fixed-width integer pixel value in this repo divides/multiplies by `2**bit`, never by `2**bit - 1` — matching how real hardware normalizes via a bit-shift rather than a division by the true max representable value. This applies consistently to `BenchmarkLoader._load_idx`'s load-time normalization above, `utils.py::RawUtils.bayer2rgb`'s internal 16-bit quantize/dequantize around the OpenCV demosaic call (multiplies/divides by `65536`, though the clip bound stays `65535` — that's the largest value a `uint16` container can hold, a separate concern from which constant defines "full scale"), and `tile_infer_hw.py`'s `to_fixed`/`from_fixed`/`round_shift` helpers. `tile_infer_hw.py` additionally has to recover the exact original integer from `BenchmarkLoader`'s float32 output before doing its own fixed-point math (`* (2 ** meta.raw_bitWidth)`, matching the loader's constant exactly) — this one is un-doing the loader's specific normalization, not applying the general fixed-point convention, so keep it in lockstep with `BenchmarkLoader` if that ever changes again. `run_benchmark_pytorch.py::save_bayer_raw` already followed this convention (multiply by `2**bitWidth`, clip to `2**bitWidth - 1`) before the others were brought in line with it. Since `run_benchmark_meg.py` also imports `BenchmarkLoader` from `dataset/benchmark.py`, this convention change silently shifts its numeric output too (by ~1 part in `2**raw_bitWidth`, e.g. ~1/65536 for the 16-bit benchmark data) even though its own script file is otherwise kept byte-for-byte original.

## Processing pipeline (run_benchmark_pytorch.py / run_benchmark_meg.py)

The eval pipeline for each sample:

1. **Bayer pattern → canonical RGGB** — `RawUtils.to_canonical_rggb(*, pattern)` flips each sample's raw array from its own `meta.bayer_pattern` into the canonical RGGB layout (top-left pixel = R) that the rest of the pipeline assumes; this is an involution (self-inverse), so calling it again with the same `pattern` later converts back. (The MegEngine script instead hardcodes this as `RawUtils.bggr2rggb`, which only handles `BGGR`.)
2. **KSigma noise normalization** — `KSigma` maps sensor ISO to a fixed "anchor" ISO's noise level (polynomial K/Sigma coefficients are hardcoded in the benchmark script), applied before inference and inverted after.
3. **Bayer → RGGB planes** — `RawUtils.bayer2rggb` packs the 2x2 canonical bayer array into 4-channel RGGB planes before feeding the network; `RawUtils.rggb2bayer` reverses this after inference.
4. **Padding** — `Denoiser.pre_process` pads the raw bayer array (before `bayer2rggb`) up to a multiple of 32 (in RGGB-plane space; the network downsamples 4x via 4 encoder stages) and crops symmetrically after. Uses `np.pad(..., mode='reflect')` (no edge-pixel duplication) rather than zero/`'constant'` padding, and the pad amount is always even (`2*ph`/`2*pw` raw pixels) — both required to keep the correct bayer color at each mosaic position across the seam (e.g. row `R0 G0 R1 G1` padded 2 cols each side must become `R1 G0 | R0 G0 R1 G1 | R1 G0`, not `G0 R0 | ... | G1 R1`, which is what edge-duplicating reflect — `mode='symmetric'`/`cv2.BORDER_REFLECT` — would produce). Zero-padding was the original approach here and measurably hurt denoising quality right at the image border (confirmed by diffing tiled vs. full-image inference: a ~10x error spike confined to the outermost ~4px, gone after switching to this reflect scheme). `tile_infer.py`'s `TiledOnnxDenoiser.run` applies the same scheme (padding by `margin` RGGB-plane pixels) before tiling, for the same reason.
5. **Inference** — `Denoiser.run` scales input by `inp_scale` (256.0), runs `Network`, rescales output back down. The result is still a canonical-RGGB-layout bayer array.
6. **RGB conversion** — `RawUtils.bayer2rgb` applies white balance, demosaics with OpenCV (`COLOR_BAYER_BG2RGB_EA`), applies the CCM, and gamma-corrects (2.2), then `to_canonical_rggb` flips the RGB image back to the original orientation. This runs on the **full image** for all three of input/pred/gt; PSNR/SSIM then crop to `meta.ROIs` afterward — cropping happens on separate patch variables, so the full-size RGB arrays are also what `--save-dir` writes out as PNGs.
7. PSNR/SSIM (via `skimage.metrics`) are computed per-ROI and averaged across the whole dataset.
8. **`--save-dir` (pytorch script only)** — per sample, writes `{name}_input.png`/`{name}_pred.png`/`{name}_gt.png` (full-image RGB, BGR uint8 for `cv2.imwrite`) and `{name}_pred.raw` (the denoised bayer result, flipped from canonical back to the sample's original `bayer_pattern` via `to_canonical_rggb` again, saved as raw uint16 — same format as the input `.raw` files).

`utils.py::RawUtils` is a set of stateless classmethods for all Bayer/RGGB/RGB conversions — reuse these rather than reimplementing raw-image reshaping.

## Training (train_pytorch.py, dataset/training_pytorch.py)

Added later by the upstream authors as `train_meg.py`/`dataset/training.py` (MegEngine); ported here to `train_pytorch.py`/`dataset/training_pytorch.py` (**the one to actually use** — MegEngine can't run on this dev machine at all, see Overview). The two were kept in sync by hand for the bugs found while porting (see below), but **that stopped being the policy once one of these bugs (the `inp_scale` normalization fix) needed real execution to even discover, let alone verify — per the user, `dataset/training.py`/`train_meg.py` are intentionally left un-fixed and will keep diverging from the PyTorch versions**, since MegEngine can't be run or checked here at all.

- **Different data format from the benchmark/inference side entirely**: no paired real noisy/gt captures here. `dataset/training_pytorch.py::CleanRawImages` loads an `index.json` of `RawImageItem`s (`path`/`width`/`height`/`black_level`/`white_level`/`bayer_pattern`/`g_mean_01`) pointing at **clean** (well-exposed, low-noise) raw images — noise is synthesized on top of these at train time, not captured. `random_flip_and_crop` does random-crop + random-flip + bayer-pattern-normalize-to-RGGB in one step (offsets the crop's top-left corner by 0/1 per source `bayer_pattern`, then XORs that offset when a flip is applied, so the result is always canonical RGGB regardless of which flip got picked) — a different technique than the inference side's `RawUtils.to_canonical_rggb` table flip, but the same goal.
- **`DataAug.transform` is where synthetic noise + KSigma normalization happen**, per batch: scale by `camera_value_scale` (959.0, same constant as inference's `KSigma.V`) → **brightness augmentation** (randomly darken toward a log-uniformly sampled target in `target_brighness_range`, clamped to never brighten — can't invent detail that isn't there) → **synthesize sensor noise** via a real Poisson (shot noise) + Gaussian (read noise) model at a randomly sampled `iso ∈ iso_range`, then round (simulating ADC quantization) → **KSigma-normalize** both the noisy image and the clean target to the `anchor_iso` noise level, using the *same* `cvt_k`/`cvt_b` formula as inference's `KSigma` class → **finally rescale to the network's actual input magnitude** (`/ camera_value_scale * inp_scale`), matching `KSigma.__call__`'s trailing `/ V` plus `Denoiser.run`'s separate `* inp_scale` at inference (see bug list below — this last step was missing entirely until just now). **This confirms where `KSigma`'s `K_coeff`/`B_coeff`/`anchor`/`V` constants are meant to come from** — training and inference must use the same calibration for a given sensor to be self-consistent (relevant to the earlier-documented cross-sensor int8 quality issue: this network/KSigma combo is only ever trained against the noise physics of whichever sensor these constants were calibrated for).
- **`DataAugOptions` is built from individual CLI options, not a `--data-aug-config` JSON file** — `train_pytorch.py`'s `add_data_aug_args`/`build_data_aug_options` (reused as-is by `train_qat_pytorch.py`) expose every field as a flag (`--k-coeff`/`--b-coeff`/`--noise-value-scale`/`--camera-value-scale`/`--anchor-iso`/`--inp-scale`/`--iso-range`/`--output-shape`/`--target-brightness-range`), defaulting to the Reno 10x calibration (matching `run_benchmark_pytorch.py`'s `KSigma(...)` exactly), since that's this repo's only actual target sensor. This is a real distinction, not just a syntax swap: the first six are **sensor-calibration constants** (fixed for a given sensor, hardcoding them as defaults loses nothing), while `--iso-range`/`--output-shape`/`--target-brightness-range` are **training-strategy knobs** unrelated to sensor calibration — `--iso-range` in particular is the cheap lever (a CLI flag, not new captured data) for widening high-ISO coverage during QAT fine-tuning discussed above, so it deliberately stayed a separate, easily-overridden option rather than being folded into the sensor constants. `DataAugOptions.parse_file` (JSON loading) still exists in `dataset/training_pytorch.py` for anyone who wants it, but neither training script uses it anymore.
- **Loss**: `get_loss_l1` (defined in `train_pytorch.py` itself, not `models/net_torch.py`) is `mean(|pred - label|)` per sample, divided by that sample's `cvt_k` before averaging over the batch — normalizes loss magnitude across the randomly-sampled ISOs in a batch (low ISO has larger `cvt_k`, i.e. the image was scaled up more to reach anchor noise level, so an unnormalized absolute error there would be proportionally smaller "real" error than the same absolute error at high ISO).
- **Bugs found while reading/porting this code** (see `dataset/training_pytorch.py`'s module docstring for the full list): `BayerPattern(Enum, str)`'s base-class order (raised `TypeError` at import, i.e. `dataset/training.py` could not even be imported as originally written), `DataAug.add_noise` missing its second return value (`isos`), a dead/unreachable branch in `train_meg.py`'s LR schedule, `CleanRawImages.__init__` discarding its own `opts` argument (`self.opts = DataAugOptions` instead of `self.opts = opts`), a missing channel-last→channel-first permute before the network (RGGB packing produces `(H,W,4)`; `Network` expects `(N,4,H,W)`), `DataAug.k_sigma`'s `cvt_k`/`cvt_b` needing a `(-1,1,1,1)` reshape before broadcasting against the image batch (bare per-sample values would only broadcast correctly by accident, if batch size happened to equal 4) — these five were fixed in both the MegEngine and PyTorch versions (before the sync policy above changed) — and, found later and **fixed in the PyTorch version only**: `DataAug.transform` ended right after the KSigma affine (`* cvt_k + cvt_b`), with no equivalent of inference's trailing `/ V * inp_scale` — every training-time network input was `camera_value_scale / inp_scale` too large in magnitude (~3.75x for the Reno 10x defaults, confirmed numerically, constant across iso). Fixed by adding an `inp_scale` field to `DataAugOptions` (default `256.0`, matching `export_onnx.py`/`run_benchmark_pytorch.py`'s own default) and applying `/ camera_value_scale * inp_scale` at the end of `transform`; verified by reproducing the inference-side formula independently for a fixed iso/pixel value and confirming an exact match (76.8 both ways) with the training augmentation's randomized steps (brightness darkening, noise synthesis) neutralized.
- **Dependencies**: the PyTorch port drops `pydantic`/`megfile`/`loguru` (not installed in `AIISP_init`) in favor of `dataclasses` (matching `dataset/benchmark.py::RawMeta`'s style) and plain `pathlib`/`open`.
- **Verification**: `train_pytorch.py` was actually run end-to-end (a few steps, synthetic tiny dataset) — loss came out finite/sane, and the saved checkpoint `load_state_dict`s cleanly into `Network()`, confirming compatibility with the rest of the PyTorch pipeline (`run_benchmark_pytorch.py`, `export_onnx.py`, ...); re-run again after the `inp_scale` fix above with the same result. The MegEngine side of the first five bugs is only syntax-checked, never run — MegEngine isn't installed here — and now (per the sync-policy change above) doesn't have the `inp_scale` fix at all.

## ONNX export & tiled inference (export_onnx.py, tile_infer.py)

- `export_onnx.py` exports `models/net_torch.py::Network` to a **fixed-shape** ONNX graph, input/output `(1, 4, height, width)`, `--height`/`--width` default `256`/`256` and must be multiples of 32. `--dtype fp32|fp16|int8`: `fp32` is a normal export; `fp16` exports fp32 first then casts the *graph* (weights + tensor dtypes) to float16 via `onnxconverter_common` — the model is never actually run in fp16 (this CPU PyTorch build has no fast fp16 conv kernel); `int8` is a reserved no-op that prints why it isn't implemented here (needs calibration-based post-training quantization, not a plain cast — see `quantize_onnx.py` below, a separate script) and returns without writing a file. After exporting, it round-trips a dummy input through both the ONNX graph (via onnxruntime) and the original PyTorch model and prints the max abs diff as a sanity check.
  - `--bake-ksigma` additionally exports the ISO-dependent KSigma normalize/denormalize affine transform *into* the graph (`KSigmaModule`/`NetworkWithKSigma`), rather than leaving it to be applied externally in numpy (the default, matching `Denoiser`/`TiledOnnxDenoiser`). This is a real design choice, not a hard constraint — KSigma is pure elementwise tensor math (`K(iso)`/`Sigma(iso)` are low-degree polynomials in `iso`, no branching on its runtime value), so it traces into ONNX ops fine; with the flag on, the graph takes a *second* input `iso` (a 1-element tensor, never baked in as a constant) alongside `input`. `--k-coeff`/`--b-coeff`/`--anchor`/`--v` override the (Reno 10x-calibrated) defaults for a different sensor. Keeping KSigma external (the default) makes swapping noise calibration a config change instead of a re-export, and keeps the graph a "pure" CNN for e.g. future int8 calibration; baking it in makes the graph self-contained for deployment targets that can't easily run custom pre/post-processing.
- `tile_infer.py` runs a fixed-shape ONNX export over real (arbitrary-size) raw images. It reuses `KSigma`/`Denoiser`/`save_rgb_png`/`save_bayer_raw` from `run_benchmark_pytorch.py` and `BenchmarkLoader`/`RawUtils` — same bayer-pattern/KSigma/RGB-conversion/raw-bitWidth handling as the other benchmark scripts, just with the network forward pass replaced:
  - `tile_positions`/`ownership_bounds` — 1D helpers computing overlapping tile start positions and non-overlapping "ownership" slices for stitching (same scheme as `../DnCNN-PyTorch_Saoyan/tile_infer.py`, generalized from 1-channel grayscale to PMRID's 4-channel RGGB planes).
  - `tiled_infer_rggb` — splits a full-size `(H, W, 4)` RGGB-plane array into `tile_h x tile_w` (the ONNX graph's baked-in shape) tiles with `--margin` pixels of overlap, runs each through the onnxruntime session, and stitches results back using `ownership_bounds` (each final pixel comes from whichever tile "owns" that region, cutting overlaps at the midpoint). Reflect-pads if the image is smaller than one tile. Note tile size is in **RGGB-plane space** — a 256x256 ONNX tile covers a 512x512 region of the original bayer image.
  - `TiledOnnxDenoiser` — same KSigma-normalize → `bayer2rggb` → (now tiled) inference → un-normalize → `rggb2bayer` flow as `Denoiser.run`, but backed by `tiled_infer_rggb` over onnxruntime instead of one single-shot padded-to-32 PyTorch forward pass. Its `bake_ksigma` flag must match whether `--onnx` was actually exported with `export_onnx.py --bake-ksigma`: when true, it skips the external KSigma/inp_scale step entirely and instead feeds the raw `[0,1]` RGGB tile plus a per-image `iso` value straight into the graph (as its second declared input) for every tile — `main()` cross-checks `--bake-ksigma` against the ONNX model's actual declared input count (1 vs 2) and raises a clear error on mismatch rather than silently double-normalizing or failing deep inside onnxruntime.
  - `--compare-full PATH` additionally runs the same sample through the untiled PyTorch `Denoiser` (loaded from a checkpoint at `PATH`) and prints the diff vs the tiled ONNX result, to help tune `--margin`. In testing, increasing `--margin` (32→96) didn't shrink the observed diff (~0.037 max, ~4e-4 mean on a `[0,1]` scale) — it appears dominated by ONNX-runtime-vs-PyTorch floating-point kernel differences rather than tile-seam artifacts, so don't assume a bigger margin alone will close this gap.
  - `--dtype fp32|fp16|int8` describes the ONNX graph's own declared **external** input/output tensor dtype (what numpy dtype must be fed in/read back) — **not** whether the graph is quantized internally; these are independent. `fp32` (default) covers both a plain `export_onnx.py` export and an int8-quantized `quantize_onnx.py` model: quantization's default `QuantFormat.QDQ` only wraps *internal* weights/activations in QuantizeLinear/DequantizeLinear pairs and deliberately keeps the graph's external boundary as `tensor(float)` (confirmed empirically — `sess.get_inputs()[0].type` is still `'tensor(float)'` after quantization), so an int8-quantized model is fed/read exactly like a plain fp32 one here. `fp16` is for an `export_onnx.py --dtype fp16` export specifically, which does a genuine graph-level type cast (`keep_io_types=False`) that changes the declared external tensor type itself. `int8` is rejected outright — no export this repo produces ever declares a genuinely int8 external input/output, so there's no dtype to actually feed; it's kept as a CLI choice only to fail loudly (mirroring `export_onnx.py`'s options) rather than silently mishandling some future model this script doesn't know how to talk to.

## Post-training int8 quantization (quantize_onnx.py)

`export_onnx.py --dtype int8` is a placeholder that refuses to run — this script is where actual int8 PTQ (post-training static quantization) lives, since it needs calibration data, unlike the plain dtype cast `--dtype fp16` does. PTQ via `onnxruntime.quantization.quantize_static` is what's implemented here; QAT (fake-quant ops inserted during training, so the network adapts to quantization noise) is a separate, complementary step — see `train_qat_pytorch.py` below — that still ends by calibrating its output through this same script, not a replacement for it.

- **Must quantize the plain (non-`--bake-ksigma`) fp32 graph**, checked and rejected otherwise with a clear error. Two reasons: KSigma has no weights of its own (pure elementwise math, nothing to quantize), and if baked in, its `iso` input would need calibrating too — real ISOs span roughly 100–25600, and representing that whole range with one int8 scale would be extremely coarse. `quantize_onnx.py` also rejects a `--dtype fp16`-exported source graph (`quantize_static` needs a `tensor(float)` input).
- **Calibration tiles** (`collect_calibration_tiles`) are extracted from a real benchmark dataset (`--benchmark`, same `benchmark.json`/`meta_info.json` format as the other scripts, loaded via the same `BenchmarkLoader`) — only the noisy `input` image is used (never `gt`), since that's the only thing the network ever sees in real deployment. Each sample is converted to canonical RGGB and KSigma-normalized (× `inp_scale`) using **that sample's own real ISO**, so the calibration data lands in the exact float32 domain the graph's `input` tensor actually receives at inference — calibrating on un-normalized pixel values would give a systematically wrong scale/zero-point. Tiles are then cropped out with `tile_infer.py`'s `tile_positions` helper reused as a non-overlapping grid (stride = tile size, no margin needed — calibration just needs a representative sample of the activation distribution, not a stitched output). Images smaller than one tile (in RGGB-plane space) are skipped with a printed warning, not silently dropped; if the whole dataset runs dry before reaching `--num-tiles`, that's also printed rather than silently returning fewer tiles.
- **Defaults**: `--quant-format qdq` (the default) — confirmed empirically that a QDQ-quantized graph's `sess.get_inputs()[0].type` is still `tensor(float)` (only weights/activations are int8 internally, wrapped in QuantizeLinear/DequantizeLinear pairs) — so a QDQ int8 model runs through `tile_infer.py` completely unmodified with `--dtype fp32`, no separate int8 I/O handling needed there. `--per-channel` defaults on (recommended: this network is mostly depthwise-separable convs whose per-channel weight magnitudes vary a lot — per-tensor quantization would be much lossier here). `--calibrate-method minmax` matches onnxruntime's own default; `entropy`/`percentile` are exposed as slower-but-more-outlier-robust alternatives if minmax's accuracy hit is too large.
- **A quantized model is never trusted automatically** — `main()` prints a reminder after quantizing, but doesn't itself verify. Re-run PSNR/SSIM (or at least `tile_infer.py --compare-full`) against the fp32 baseline before using an int8 export for anything real. In a quick smoke test here (40 calibration tiles, one sample), the int8 model came out ~3.1x smaller (1.34 MB vs 4.17 MB fp32) and `tile_infer.py --dtype fp32 --compare-full` showed mean abs diff 3.7e-3 vs untiled fp32 PyTorch — about an order of magnitude above the fp32-onnx-vs-PyTorch kernel-only baseline (~4e-4), which is expected from quantization noise on top of that baseline, not itself a full accuracy validation.
- **Different int8 deployment targets are not guaranteed to match, even given the identical model file** — different quantization schemes (symmetric/asymmetric, per-channel granularity, weight/activation dtype, calibration method) produce different quantized weights, and even the same int8 model can execute differently across runtimes (reduced-precision accumulation, different requantization rounding, unsupported-op fallback paths). Validating this int8 export against onnxruntime's own CPU execution is not a proxy for how it'll behave on a different int8 runtime/accelerator — see `AI_CMODEL_INTEGRATION.md` for the fuller discussion; re-verify per actual deployment target.

### Known issue: severe int8 quality loss on out-of-domain (different sensor / high ISO) data — investigated, unresolved by PTQ tuning

Calibrating on `dataset/benchmark/benchmark.json` (Reno 10x, `BGGR`, ISO 800–6400) and then running that int8 model on `dataset/test/meta_info.json` (a different sensor, `GBRG`, ISO up to 25600) produces **subjectively unacceptable** denoising quality, even though fp32/fp16 on the same `dataset/test` data look good (confirmed by the user visually — subjectively better than that dataset's own imperfect `gt.raw`, so fp32 output, not PSNR/SSIM-vs-gt, is the right baseline to quantize against here). A thorough investigation ruled out the easy fixes:

- **Not calibration coverage**: merging `dataset/test` samples into the calibration set (same ISO/sensor as the deployment target) did not improve the result — even slightly worsened it. Broadening *what* the calibrator sees isn't the lever. **Reconfirmed later, more strongly**: `dataset/calibrate/calibrate.json` was subsequently expanded to 47 entries spanning ISO 800–25600 and now *literally includes the exact 8 `dataset/test` samples themselves* (calibrating on the very images later used for evaluation) — the severe degradation still reproduces identically. Calibration coverage was never the bottleneck.
- **`--calibrate-method` matters some, but plateaus**: `minmax` (default) → `percentile` gave a real ~30% mean-abs-diff improvement (vs. untiled fp32 PyTorch, on a held-out high-ISO sample) — the best single lever found. `entropy` was worse than `minmax`. Increasing `--num-tiles` for `percentile` from 40→80→100 gave only ~9% further improvement, with clearly diminishing returns (this dev machine's practical memory ceiling for `percentile`/`entropy` histogram collection is ~100-120 tiles, not 40 — `quantize_static`'s memory use grows with tile count for these two methods, unlike `minmax`).
- **Not concentrated in specific layers**: a per-module-group sensitivity sweep (excluding `conv0`/`enc1`-`enc4`/`encdec`/`dec1`-`dec4`/`out0`/`out1` one at a time from quantization, keeping everything else int8) found no group whose exclusion meaningfully closes the gap — best case (`enc2`) was +6.3% mean-diff improvement, several groups were within ±1% noise, and excluding `enc3` made results *worse* (-6.7%). This rules out a simple mixed-precision fix (keep a couple of "sensitive" layers in fp32, quantize the rest).
- **Activation quantization type** (`QInt8` vs `QUInt8`) made no measurable difference either.
- **QAT (see `train_qat_pytorch.py` below) does not close the gap either**, at least not at the scale tried so far — see that section for the full result.

**Root cause identified (this explains all of the above "didn't help" findings at once)**: KSigma's `cvt_k(iso) = k(anchor)/k(iso)` compresses the *entire* image (signal and noise together) toward the anchor ISO's level — measured directly from the real `K_coeff`/`B_coeff`/`anchor` constants: `cvt_k` = 1.98 at ISO 800, 1.00 at the anchor (1600), and only **0.063 at ISO 25600** — a ~31x shrink in overall activation magnitude between the low and high end of the range this network actually sees in `dataset/calibrate.json`/`dataset/test`. This was confirmed against *real* calibration-tile data too: measured activation std/min/max at ISO 800 vs. 1600 vs. 6400 tiles shrink in almost exactly this same ratio. **fp32 is completely insensitive to this** — floating point keeps full relative precision at any magnitude, which is exactly why fp32/fp16 look great at every ISO in `dataset/test`, including 25600, with the very same KSigma constants. **Static per-tensor/per-channel int8 quantization is not**: `quantize_static` bakes in *one* fixed scale per activation tensor, computed once from calibration data spanning the *whole* ISO range — that single scale is necessarily dominated by the large-magnitude low-ISO activations, leaving only a handful of effective quantization levels for the ~31x-smaller high-ISO ones. This is why broadening calibration coverage, trying different calibrate-methods, excluding layers, and (per the QAT section below) fine-tuning the weights all failed to fix it: none of those touch the actual mismatch, which is that **one static scale cannot represent values spanning >30x of dynamic range with adequate relative precision, regardless of how well-covered or well-fine-tuned everything else is.**

**Ways forward**:
1. If the real deployment hardware also has accelerated fp16 (not int8-only), fp16 sidesteps this entirely — it's a deterministic dtype cast, not a calibrated quantization, so it has none of the above failure modes (already confirmed to look good on `dataset/test`). Only viable if the target actually accelerates fp16, not just "can run it."
2. QAT (quantization-aware training, `train_qat_pytorch.py`) — **tried on real data, did not close the gap** (see that section). Consistent with the root cause above: QAT reshapes weights, not the fact that activation magnitude varies ~31x by ISO, so it was never going to fix this specific failure mode.
3. **Dynamic quantization — tried, confirmed this is the actual fix (for onnxruntime-CPU deployment specifically), now a real CLI option: `quantize_onnx.py --dynamic`** (routes to `onnxruntime.quantization.quantize_dynamic`, no `--benchmark` calibration set needed at all — `--num-tiles`/`--calibrate-method`/`--activation-type`/`--quant-format` are ignored in this mode). Tested first as a standalone `quantize_dynamic(...)` call on the plain vanilla fp32 graph, then confirmed identical output via the actual `--dynamic` flag: inspecting the resulting graph confirms 88 `Conv` nodes became `DynamicQuantizeLinear`+`ConvInteger` pairs (activation scale computed fresh from the actual tensor on every inference call, not baked in from calibration) — only the 4 `ConvTranspose` nodes (one per `DecoderStage`) stayed fp32, un-quantized (no dynamic-quant kernel support for that op, same ConvTranspose quirk seen elsewhere in this project). Declared external I/O is still plain `tensor(float)`, so it drops into `tile_infer.py --dtype fp32` completely unmodified. Run on the same 8 `dataset/test` high-ISO images used throughout this investigation: mean abs diff vs. fp32 dropped from **0.012–0.043 (static) to 0.0022–0.0034 (dynamic)** — a ~10-15x improvement — and, critically, the dynamic numbers no longer grow with ISO the way the static ones did (they'd tracked the ~31x `cvt_k` compression almost exactly; now they're roughly flat across all 8 samples regardless of ISO). This is direct, strong confirmation of the root-cause diagnosis above: a *dynamic* per-call scale sidesteps the "one static scale can't span 30x of magnitude" problem entirely, because there's no longer a single shared scale across ISOs to begin with. Visual check (same sample shown blown-out under static quant earlier) now looks indistinguishable from the fp32 render. Caveat: the 4 un-quantized `ConvTranspose` ops mean this isn't a "pure" int8 graph, and dynamic quantization's per-call scale computation has real runtime cost vs. static's baked-in constants — worth profiling before assuming it's a free win on the actual target hardware, especially if that hardware isn't onnxruntime-CPU (this fix is specific to a runtime that actually supports computing quantization parameters at inference time; a fixed-function int8 accelerator that only accepts pre-baked static scales would need option 4 below instead).
4. **"Option B" for deployment targets that can't do dynamic quantization — tried, does NOT work, ruled out on the math itself, not just an empirical shortfall.** The idea (an external per-frame rescale, applied outside a static-quantized graph, that would cancel `cvt_k(iso)`'s magnitude compression before the network and undo it after) was implemented (`tile_infer.py`/`quantize_onnx.py --iso-rescale`, since removed) and looked promising at first (mean abs diff vs. fp32 dropped from 0.012–0.043 to 0.007–0.029 on the same 8 high-ISO `dataset/test` samples) — **but that comparison was against the wrong reference, and the apparent improvement was an illusion.**

   Deriving what the rescale actually computes: `net_input = img01*cvt_k*inp_scale + cvt_b*inp_scale/V` (KSigma + inp_scale, the same per-frame affine `tile_infer_hw.py` collapses these into). The proposed rescale was `net_input' = net_input*g + h` with `g = 1/cvt_k`, `h = -B/cvt_k` (where `B = cvt_b*inp_scale/V`) — substituting through: `net_input' = img01*inp_scale`, **exactly**, for every ISO, confirmed both algebraically and numerically (e.g. at ISO 25600, `net_input` before the rescale is 4.55, after is 76.80 — identical to what `img01*inp_scale` gives directly, and identical to what ISO 1600 produces with no rescale at all). **This is not "cancelling an incidental magnitude side effect while preserving KSigma's noise-normalization" — it is undoing KSigma's noise-normalization completely**, back to the raw, un-normalized, actual-ISO noise level. The scale-invariant-SNR reasoning used to justify this was wrong: `cvt_k` is not a generic multiplier a caller can freely strip off — it *is* the specific multiplier that maps the real, ISO-dependent noise level onto the anchor's target level. Magnitude compression and noise-level normalization are the same multiplication here, not separable — cancel one and the other necessarily goes with it.

   Confirmed with real data: running the **fp32** (unquantized) model with this rescale applied, vs. the same fp32 model without it — no quantization involved anywhere — already shows mean abs diff 0.006–0.031 (max up to 0.49) on the 8 `dataset/test` samples, worse at higher ISO. This is the rescale silently discarding the correct denoising strength (feeding the network what looks like anchor-ISO noise when the actual noise is far higher), not a rounding artifact. Redoing the original int8 comparison against the *correct* reference (fp32 with the same rescale applied, not fp32 without it) shows the actual quantization-only error on top of this broken transform is just 0.004–0.007 — fine on its own, but irrelevant, since the transform beneath it already discarded the correct answer. The earlier "~35-40% improvement" number was an artifact of comparing against the wrong baseline; the real picture is that this approach doesn't work at all, and has been removed from the code — dynamic quantization (option 3) is the only fix that has actually held up here, and a deployment target that cannot do dynamic quantization does not have a working int8 fix from this investigation for the high-ISO case.

### Side effect of `--dynamic` + tiling: quantization noise character varies block-to-block, tracking tile ownership regions

Noticed by the user comparing `_pred.png` diff images: `vanilla fp32` vs. `vanilla --dynamic int8` (same model) shows a **blocky** pattern of local noise variance — the same kind of flat scene content can show visibly different diff variance depending which spatial block it falls in, block size roughly matching `tile_infer.py`'s tile-ownership regions (~284–448px in bayer-pixel space for `dataset/test`'s 1080x1920 images, at the default `--margin 32`/256x256-tile export — computed exactly via `tile_positions`/`ownership_bounds`). Critically, this blockiness is **absent** comparing two different fp32 models (`vanilla fp32` vs. `QAT fp32`) on the same images — that diff's variance is spatially uniform. This observation itself was the key diagnostic: it isolates the effect to quantization specifically, not to tiling/stitching in general (which both comparisons share equally).

**Root cause, directly verified (not inferred from the noisy image comparison alone)**: `tiled_infer_rggb` calls `sess.run()` once per tile, in a loop — and `DynamicQuantizeLinear` computes its scale fresh from *that call's own input tensor*, not from a shared constant. Confirmed by adding the `y_scale` outputs of several `DynamicQuantizeLinear` nodes to the graph (via `onnx.helper.make_tensor_value_info` + re-saving) and feeding two synthetic tiles of different magnitude through the modified session directly: a tile with range `[0, 5]` gave scale `0.0196`; a tile with range `[0, 150]` (30x larger) gave scale `0.588` (also ~30x larger) — proving each tile's forward pass really does get its own independently-computed scale, tied to whatever that specific tile's own activation range happens to be.

This means each tile's int8 rounding precision depends on *everything in that tile* (e.g. a bright highlight elsewhere in the same 512x512 bayer region raises that tile's scale, coarsening quantization for every pixel in the tile, including unrelated flat regions elsewhere in it) — not just the local patch a viewer happens to be looking at. Two visually-similar flat patches landing in two different tiles can end up with genuinely different quantization noise levels if their respective tiles' *other* content differed, which is exactly what produces the tile-sized blockiness in the diff map.

**Not a bug**: `ownership_bounds`/`tile_positions` themselves are correct (non-overlapping, gapless tiling, confirmed by construction and by the fact that the *fp32-vs-fp32* comparison — which exercises the identical tiling/stitching code path, only without quantization — shows no such blockiness). This is an inherent consequence of combining a fixed-shape *tiled* ONNX export with *dynamic* per-call quantization, not a stitching defect or a `quantize_onnx.py` defect. It doesn't change the headline result (dynamic quantization's overall error, 0.0022–0.0034, is still far below static's 0.012–0.043) — it describes the *spatial texture* of that already-small error, not its magnitude. If the blockiness itself matters for a downstream use case (e.g. feeding a block-sensitive ISP stage after this), the lever would be a larger tile/export shape (fewer, bigger tiles → fewer distinct scale regimes → less visible blockiness, at the cost of more compute per tile) — not yet tried.

## QAT (quantization-aware training) fine-tuning (train_qat_pytorch.py)

Answers the question raised while investigating the int8 issue above: if `quantize_onnx.py` (PTQ) is still needed after QAT anyway (since PyTorch's own `convert_fx()` can't produce a deployable model here — see next paragraph), what does QAT even buy? Calibration itself is identical either way; what QAT changes is the float weight distribution being calibrated, reshaping it (for whatever domain it was fine-tuned on) to tolerate int8 rounding better — it moves the coverage question from "did `quantize_onnx.py`'s calibration set see enough" to "did QAT's fine-tuning data see enough," which is cheaper to fix (synthetic ISO range in `--data-aug-config` is a config change, not new captured images).

- **Fine-tunes from the existing fp32 checkpoint**, not from scratch: loads `--init-ckp` (defaults to `models/torch_pretrained.ckp`) into `Network()`, wraps it with `torch.ao.quantization.quantize_fx.prepare_qat_fx` using `get_default_qat_qconfig(--backend)` (default `onednn`, which fake-quantizes weights per-channel symmetric int8 — matching `quantize_onnx.py`'s own `--per-channel` default), then fine-tunes with the same `dataset/training_pytorch.py::CleanRawImages`/`DataAug` pipeline and `get_loss_l1` as `train_pytorch.py`. Meant to be brief (`--num-epoch` defaults to 10, `--learning-rate` defaults to `1e-5` — much smaller than from-scratch training) since this is adapting already-converged weights to fake-quant noise, not learning the task from zero. `--batch-size` defaults to 4 (see CPU batching note below).
- **`convert_fx()` is deliberately never called.** PyTorch's native quantization backend raises `RuntimeError: Per Channel Quantization is currently disabled for transposed conv` on `convert_fx()` for any per-channel qconfig — confirmed empirically — and every `DecoderStage` here uses a `ConvTranspose2d` for its 2x upsample, so a per-channel `convert_fx()` model is a dead end for this architecture (a global per-tensor qconfig does `convert_fx()` successfully, and replacing `ConvTranspose2d` with `Upsample+Conv2d` also sidesteps the restriction, but both were confirmed-working workarounds not worth taking — the former loses per-channel accuracy, the latter is an unnecessary architecture change — since `quantize_onnx.py`/onnxruntime's `quantize_static` already handles `ConvTranspose2d` per-channel quantization correctly with no such restriction).
- **Weight extraction relies on this architecture having no BatchNorm**: `prepare_qat_fx` swaps each `Conv2d`/`ConvTranspose2d` for its `nn.qat.*` counterpart in place (same qualified name, real fp32 `.weight`/`.bias` still plain parameters, just with extra `weight_fake_quant`/`activation_post_process` buffers alongside) rather than fusing/restructuring the module graph the way it would if there were BatchNorm layers to fold in. So after training, `extract_float_state_dict` just intersects the QAT-prepared model's `state_dict()` keys against a plain `Network()`'s (a strict subset) and saves those — loadable exactly like `models/torch_pretrained.ckp`, and meant to be fed through the existing `export_onnx.py` (fp32) → `quantize_onnx.py` (PTQ) pipeline unmodified.
- **Best-checkpoint tracking**: each epoch's mean training loss (there's no held-out validation split in this pipeline) is compared against the best seen so far; an improvement saves `epoch_best_{epoch}.ckp` and deletes the previous best file, so exactly one "best" checkpoint exists at any time, alongside the regular per-epoch `epoch_{epoch}.ckp` files (`--save-every`, default every epoch). **Use the best checkpoint, not the last epoch, when evaluating** — training loss is not monotonic (see the real run below), so the final epoch is not necessarily representative.
- **CLI is individual options, not a `--data-aug-config` JSON file**: shares `add_data_aug_args`/`build_data_aug_options` with `train_pytorch.py` (see Training above) — same Reno 10x-calibrated defaults for the six sensor-calibration constants, plus `--iso-range` (default widened to `800 25600`, to cover `dataset/test`'s higher ISOs), `--output-shape`, `--target-brightness-range` as separate training-strategy knobs.
- **Calibration for the resulting int8 export should use `dataset/calibrate/calibrate.json`** (a curated subset of `dataset/benchmark/`, since expanded to also include `dataset/test`'s own samples and ISOs up to 25600 — same `benchmark.json`-compatible schema, so `quantize_onnx.py --benchmark dataset/calibrate/calibrate.json` needs no code change) rather than the full `dataset/benchmark/benchmark.json`.
- **Plumbing verified** (tiny synthetic dataset, 2 epochs, from the real `models/torch_pretrained.ckp`): trains without error; the extracted checkpoint `load_state_dict(strict=True)`s cleanly into a plain `Network()` with **all 141 parameter tensors** different from the init checkpoint (confirming real weight updates, not a pass-through save); forward pass output is finite; re-exports/re-quantizes through the existing pipeline with no code changes needed.
- **Real-data result: tried end-to-end, does not close the int8 quality gap.** Fine-tuned on `dataset/SID_Sony_raw` (231 clean images converted from the Sony SID dataset's `.ARW` files via `dataset/convert_arw_to_raw.py`, see below), 20 epochs, `--batch-size 4`. Training loss was **not** monotonic (epoch 7 was the lowest at 7.79; epochs 8–19 bounced between ~8 and ~10.5, epoch 19 itself at 8.83) — per-channel weight magnitude only shifted ~2–5% from the init checkpoint (checked directly: max ratio of QAT/vanilla per-channel weight max was 1.05), confirming this is a genuinely light touch, not a retrain. Exported+quantized **both** `epoch_19` (the last epoch — what a naive "just use the final checkpoint" run would test) and `epoch_best_7`, and compared against the vanilla (non-QAT) fp32→int8 pipeline on the same 8 `dataset/test` images:
  - `epoch_19`'s int8 result was **1.6–1.9x worse** than vanilla's (mean abs diff vs. its own fp32, e.g. 0.073 vs. vanilla's 0.042 on the worst sample) — but this was mostly an artifact of testing a non-optimal checkpoint, not evidence QAT itself hurts.
  - `epoch_best_7`'s int8 result was **close to vanilla's, not clearly better or worse** (e.g. 0.043 vs. vanilla's 0.040 on the same sample) — confirming that a light QAT fine-tune, at this scale, does not meaningfully narrow the gap. This is consistent with the root-cause finding above (see "Post-training int8 quantization" section): the failure mode is a per-ISO activation *magnitude* mismatch that fine-tuning weights doesn't address, since the network never adjusts what magnitude a given ISO's KSigma-normalized input arrives at — only calibration or a per-ISO rescale can.
  - **Also re-tested with `--dynamic` quantization once that fix existed**: `epoch_best_7` + `--dynamic` gave results statistically indistinguishable from vanilla + `--dynamic` (0.0022–0.0034 both ways, differences within noise) — QAT doesn't help the dynamic-quant path either, at this weight-shift scale.
- **A more aggressive re-run (`--learning-rate 1e-4`, `--num-epoch 50`, 10x the LR) made things WORSE, not better — a real, useful negative result.** Weights shifted much more this time (max per-channel weight ratio 1.22 vs. the earlier run's 1.05 — a genuinely larger adaptation), best checkpoint was `epoch_best_24` (loss 6.67, still non-monotonic throughout: epochs bounced between ~6.7 and ~10.4 the whole run, no cleaner convergence than the smaller-LR run despite 2.5x the epochs). But **this checkpoint's own fp32 output had already drifted significantly from vanilla fp32** (mean abs diff 0.021–0.082 vs. the weak run's 0.004–0.013, confirmed visibly noisier in a side-by-side render) — i.e. the larger LR degraded the model's actual denoising quality, not just its quantization behavior, most likely by overfitting toward `dataset/SID_Sony_raw`'s specific small (231-image), different-sensor content at the expense of the broader quality the original checkpoint had. Its `--dynamic`-quantized result was correspondingly worse than vanilla too (0.0038–0.0053 vs. vanilla's 0.0022–0.0034) — worse than even the weak QAT run, because it's compounding quantization noise on top of an already-degraded fp32 baseline, not because quantization itself got harder. **Lesson: `1e-5` (or something close to it) is closer to the right order of magnitude for this dataset/checkpoint combination than `1e-4` — a naive "just make the learning rate and epoch count bigger" escalation actively hurts, it doesn't just fail to help.**
- **CPU batching for the fake-quant-wrapped model behaves differently than the plain model**: benchmarked separately (`prepare_qat_fx`-wrapped `Network()`, real weights, this dev machine's CPU) since fake-quant ops add per-call overhead that plain conv training doesn't have. Unlike the plain model (where batch_size=4 was *worse* per-sample than batch_size=1), here batch_size=4 gives the best per-sample throughput (451.7ms/sample vs. 522.6ms/sample at batch_size=1, ~14% faster; batch_size=8 is slightly worse than 4) — hence the `--batch-size 4` default. Learning rate was deliberately **not** scaled up for the larger batch (the common linear/sqrt scaling heuristics apply to plain SGD, not really to Adam, and QAT fine-tuning wants small, careful updates regardless).

## Training data preparation from a different sensor (dataset/convert_arw_to_raw.py)

`train_pytorch.py`/`train_qat_pytorch.py` need an `index.json` + clean raw images (see Training above) — `dataset/convert_arw_to_raw.py` builds exactly that from Sony `.ARW` files (the SID "See in the Dark" Sony subset, placed under `dataset/SID_Sony/`), producing `dataset/SID_Sony_raw/` (231 `.raw` files + `index.json`) used for the QAT runs documented above.

- **Reads the sensor's raw bayer mosaic via `rawpy`/LibRaw's `raw_image_visible`** (the active sensor area, with the optical-black border already excluded — confirmed on a real file: visible `2848x4256` vs. full-with-borders `2848x4288`) — not a demosaiced/processed image, matching this repo's convention of storing single-channel bayer arrays as plain uint16 binary files. Output filenames are suffixed `_H_{height}_W_{width}`.
- **Also runs a simple ISP** (white balance from the file's own `camera_whitebalance` as-shot metadata, demosaic via `RawUtils.bayer2rgb` with an identity CCM since no calibrated color matrix exists for this sensor, gamma 2.2) and saves a PNG per image under `SID_Sony_png/`, purely as a visual sanity check — not colorimetrically accurate.
- **`index.json` generation**: `bayer_pattern` is decoded from rawpy's `raw_pattern`/`color_desc` (confirmed `RGGB` for this camera) via a small helper that reads the 2x2 CFA tile in the same top-left/top-right/bottom-left/bottom-right order the pattern names encode; `black_level`/`white_level` are collapsed from rawpy's per-channel values to the single scalars `RawImageItem` expects (warns instead of silently averaging if a file's channels actually disagree — never triggered on this dataset, all uniform); `g_mean_01` is the mean of the G-channel pixels in `[0,1]`-normalized, canonical-RGGB space. Verified by actually loading the generated `index.json` through the real `CleanRawImages` and confirming it produces correctly-shaped `(4, 256, 256)` float32 crops with sane value ranges.
- **INPUT_DIR/OUTPUT_DIR/PNG_DIR are hardcoded constants** at the top of the script (computed relative to the script's own location, not the cwd), not CLI options, per how this script is meant to be used (edit-and-rerun for a fixed dataset layout, not parameterized per-invocation).

## Fixed-point pre/post-processing (tile_infer_hw.py)

`tile_infer.py`/`run_benchmark_pytorch.py` always cross the network's boundary in float32 `[0,1]`-ish values, even when the graph itself is int8-quantized (QDQ keeps external I/O as `tensor(float)`). That's fine when the network's own int8 inference stack is the whole deployment target, but not when PMRID is a drop-in denoise module inside an otherwise **fully fixed-point** ISP pipeline, where the upstream/downstream modules hand off/expect RAW pixel data as plain integers (e.g. RAW12) with no floating point anywhere. `tile_infer_hw.py` reimplements exactly that boundary in integer-only fixed-point arithmetic; visualization/`.raw` saving/metrics are left untouched (float32, same as the other scripts) — only the network's pre/post-processing changes.

- **Scope, agreed with the user**: `.raw` is still saved at each sample's own `meta.raw_bitWidth` via the existing (unchanged) `save_bayer_raw`, and PNG visualization/PSNR-SSIM stay on float32 `[0,1]` — the fixed-point result is converted back to float32 right after the network, before handing off to that existing code. Only requires a plain (non-`--bake-ksigma`) graph — this script applies KSigma itself, in fixed point; a baked graph would double-apply it (rejected with a clear error, same pattern as `quantize_onnx.py`/`tile_infer.py`'s other input-count checks).
- **Fixed-point convention** (as specified by the user, not invented; see also the "Normalization convention" note under Dataset layout, which this file's `raw_bitWidth`-recovery step must stay in lockstep with): given `bit_int` integer bits and `bit_frac` fractional bits, `val_fxp = clip(round(val_fp * (1<<bit_frac)), lo, hi)` where unsigned `lo,hi = 0, (1<<(bit_int+bit_frac))-1` and signed `lo,hi = -(1<<(bit_int+bit_frac)), (1<<(bit_int+bit_frac))-1` (standard two's-complement-style asymmetric range — an earlier symmetric version of the signed range was a spec bug, corrected); `val_fp = val_fxp / (1<<bit_frac)`. `round` is `round_half_up` throughout (`to_fixed`/`round_shift` in this file), for the same reason as everywhere else in this repo.
- **`--bit-module`** (default 12, i.e. RAW12): the module interface width. If a sample's `raw_bitWidth` differs, `rescale_bitdepth` converts via a **pure integer bit-shift** (round-half-away-from-zero when narrowing) — always exact since both are plain bit-depths, so their ratio is always a power of two, never a lossy general rescale.
- **KSigma collapses into one affine transform each way** (`compute_forward_affine`/`compute_inverse_affine`): algebraically, `KSigma(x,iso)*inp_scale` and `KSigma(y/inp_scale,iso,inverse=True)` both cancel `V` out completely and reduce to `net_input=img01*A(iso)+B(iso)` / `img01=net_output*C(iso)+D(iso)`. Since `iso` is one scalar per frame (not per pixel), `A/B/C/D` are computed once per frame at full float64 precision — this is the "LUT" — and only these four scalars get quantized (`--net-bit-int`/`--net-bit-frac`, default 13/18, signed); every per-pixel step after that is a single fixed-point multiply-add, no division anywhere.
- **The one unavoidable float32 crossing**: onnxruntime's graph still declares `tensor(float)` I/O regardless (see `tile_infer.py`'s `--dtype` comment), so immediately before/after `sess.run()`, the fixed-point value is converted via `from_fixed`/`to_fixed` — this is a lossless re-interpretation of an already-computed value into the required container type, not fresh floating-point computation.
- **Verified against the float32 reference** (`--compare-full`, reusing `Denoiser`): with the default bit widths, the diff vs. untiled float32 PyTorch matched the plain (non-fixed-point) `tile_infer.py` baseline almost exactly (e.g. one sample: max 1.527e-2 / mean 4.111e-4 here vs. 1.533e-2 / 4.041e-4 there) — meaning the fixed-point derivation itself adds negligible error on top of the pre-existing onnxruntime-vs-PyTorch kernel-difference baseline, for at least the ISO range tested.
- **A real bug caught by this verification, not a fixed-point precision issue**: `Denoiser.run()` never clips its own output (only `save_bayer_raw`/`bayer2rgb` do, right before actual use) — near saturated highlights (`input_bayer == 1.0`, i.e. RAW-max) the network's residual can legitimately push the float reference above 1.0 (observed up to ~1.20). This pipeline's own result is always clipped to `[0,1]` (RAW12 has no headroom past its max value), so `--compare-full` clips the float reference the same way before diffing — otherwise a handful of saturated-highlight pixels dominate the max diff with a difference that has nothing to do with fixed-point precision (one such case initially showed a spurious 0.2 max diff that dropped to the expected ~1.5e-2 range once compared fairly).

## Model architecture (models/net_mge.py, models/net_torch.py)

Both files define the **identical** encoder-decoder (U-Net-style) architecture — one in MegEngine (`megengine.module`), one in PyTorch (`torch.nn`) — kept in sync by hand. When changing the architecture, mirror the change in both files.

- `Conv2D(...)` — helper returning either a standard conv or a depthwise+pointwise separable conv (`is_seperable=True`), optionally with ReLU. Almost all convs in this network are separable (mobile-oriented design).
- `EncoderBlock` / `EncoderStage` — residual blocks with a projection shortcut when stride/channels change; 4 encoder stages (`enc1..enc4`) downsample by 2x each via stride-2 first block.
- `DecoderBlock` / `DecoderStage` — residual decode block, then `ConvTranspose2d`/`M.ConvTranspose2d` 2x upsample, fused with a projected skip connection from the matching encoder stage.
- `Network` — 4 encoder stages (16→64→128→256→512 channels) + a bottleneck (`encdec`) + 4 decoder stages back down to 16 channels, final conv predicts a **residual** added to the input (`pred = inp + x`), i.e. the network predicts the noise, not the clean image directly.
- Input/output is 4-channel RGGB, not 3-channel RGB.
